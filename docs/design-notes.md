# Design notes

Why nft-assert is built the way it is. The README says what it does; this says what was decided and what else was
considered. The decisions are in the order a reader usually asks about them.

## The problem in one paragraph

`nft -c` says a ruleset is valid. It does not say what gets through. A firewall change is usually judged by reading
the diff and reloading, and the failures are the quiet kind: a rule that opens one port too many, a rule that drops
where it should reject (the other side waits instead of being told no). The aim is to ask the question the way the
network asks it: send the packet and see what happens.

## Decisions

### Real network namespaces, not a simulator

A model of nftables (parse the JSON, walk the chains, evaluate the rules) would be a second firewall with its own
bugs. Sets, maps, NAT, connection tracking, `jump` and `goto`, verdict maps and `meta` expressions are a lot to
reimplement, and every difference between the model and the kernel would show up as a false answer. The kernel is the
reference, so the tool uses the kernel: one namespace for the firewall, one per zone, joined by veth pairs, the
ruleset loaded into the firewall namespace, real packets between them.

Not used: Docker containers (needs a daemon, slower, and the bridge adds rules of its own), `iptables`-style unit
tests that only compare text, mocks.

Cost: it needs root (or `CAP_NET_ADMIN` and `CAP_SYS_ADMIN`) and a kernel with nftables, and it tests the kernel it
runs on. Both are stated in the README.

### Verdicts are observed, not declared

* accept: a TCP handshake completed, a UDP datagram was answered, a ping came back
* reject: the sender was told no (a TCP reset or an ICMP destination unreachable)
* drop: nothing came back within the timeout

Drop is the absence of an answer, so it costs a timeout. All flows of a run are sent in parallel (up to 200 at a time
per place), so a hundred silent flows cost one timeout, not a hundred.

Every zone host and the firewall listen on every probed port. If they did not, a "reject" could come from a closed
port instead of the ruleset, and the answer would be wrong in the way that is hardest to notice.

### A sanity pass before the ruleset is loaded

Before the ruleset goes in, every flow to an address in the lab is sent once and all of them must get through. If one
does not, the run stops with "the lab is broken, not your ruleset". A lab that cannot be trusted is not allowed to
produce a verdict about your firewall. This is the check that stops a wrong "drop" from being read as a pass.

### The answering host says who it saw

The helper in each namespace answers with a line naming itself, who it thinks is calling and which address it was
reached on. That is how `[[observe]]` can check NAT and port forwards from the far side, which is where the question
actually matters ("does the web server see the client's address or the firewall's?").

### Tracing only for failures

When an expectation fails the tool wants to name the rule that decided it. It adds a helper table that turns
`meta nftrace` on for exactly that traffic, sends the flow again, and reads `nft monitor trace`. Doing this for every
flow would slow the run and bury the output, so it is done for the failures only, and the helper table is removed
afterwards.

### Strict spec, standard library only

The spec is TOML and an unknown key is an error, because a typo in `[expect.drop]` that is silently ignored would turn
a test into a pass. There are no third-party dependencies: it is a tool that runs as root in CI, so the less code it
pulls in, the less there is to trust.

### The kernel's ICMP rate limits are raised

Linux limits how many ICMP errors it sends (per peer and globally). With the defaults, the 51st simultaneous reject
would look like a drop. The limits are raised inside the lab namespaces, and if the kernel still holds an error back
the run stops with exit 3 instead of guessing.

## How it was checked

* Unit tests that need no root: the spec parser (every error message, plus mutated specs that must either parse or say
  why), the trace parser (against output recorded from a real `nft monitor trace`), the reports, the CLI, and scans of
  the source for shell strings and dynamic code.
* Live tests in real namespaces: accept, drop and nine rejecting rules, input and output chains, NAT, jumps and sets,
  the matrix and the diff, a hundred simultaneous rejects, Ctrl-C and SIGTERM leaving nothing behind, and a property
  test that turns a random truth table into a ruleset and requires the matrix to measure exactly that table.
* The README's outputs are regenerated by running the tool in CI and must equal the committed files.
* **A mutation check, once and by hand.** 45 single-line changes to lines that decide a verdict or guard the lab
  (the reject errno list, the sanity pass, the trace filter, the cleanup prefix and so on); after each change the whole
  suite ran and was required to fail. It failed for all 45. The idea of a mutation check is that passing tests prove
  little until you show they fail when the code is wrong. It is not in CI, the list is not exhaustive, and it says what
  was checked once, not what is guaranteed.

## What would be changed next

These are the limits in the README, in the order they would be tackled (see [ROADMAP.md](../ROADMAP.md)):

1. IPv6. Today the lab is IPv4 only. It is the most common question about the tool and the biggest gap.
2. Run a subset of a large spec while fixing one rule.
3. Other ICMP types as probes.
4. Rate-limited rules are order-sensitive, because flows run in parallel. A mode that runs such flows one at a time
   would make them deterministic.

## Questions this design usually draws

**Why namespaces and not Docker?** No daemon, nothing of its own in the firewall path, and network namespaces are the mechanism
containers use anyway.

**How do you tell a drop from a reject?** A reject is an answer (a reset or an ICMP error) and a drop is silence until
the timeout. The sanity pass and the listeners on every port make sure the answer comes from the ruleset.

**How can it see through NAT?** The answering host reports who it thinks called and on which address it was reached.
Comparing that with the spec's `source_seen` and `reached_port` checks the translation from the far side.

**What if the lab itself is wrong?** The sanity pass: every flow must get through with no ruleset, or the run stops.

**What does it not catch?** Anything that depends on another kernel, on IPv6, on traffic types other than TCP, UDP
and ping, on connection tracking helpers, or on hardware offload. Bridge and ingress rules are not exercised.

**How do you know the tests themselves are any good?** A property test checks the matrix against random truth tables,
and the one-off mutation check above made 45 deliberate mistakes and the suite caught each.

## Three-minute demo

```sh
pip install git+https://github.com/ErenOzgu/nft-assert
sudo nft-assert check examples/edge/spec.toml                    # all pass
sudo nft-assert check examples/edge/spec.toml \
     --ruleset examples/edge/firewall-broken.nft                 # two mistakes, named by rule
sudo nft-assert matrix examples/edge/spec.toml                   # who can reach whom
sudo nft-assert diff examples/edge/spec.toml \
     examples/edge/firewall.nft examples/edge/firewall-broken.nft # what the change opened
```

What to say: the second command shows the point. The ssh rule said `eth0` where it meant `eth1`, nothing in `nft -c`
notices, and the tool reports that the lan lost ssh and the internet gained it, with the rule that decided each one.
